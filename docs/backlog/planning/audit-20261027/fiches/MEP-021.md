## Raffinement proposé — A à G

### A. Problème utilisateur

API, workers et scripts ne peuvent être configurés depuis un contrat MESS commun livré.

### B. Valeur observable

Faire fonctionner tous les processus sur la même configuration validée avant effet. La conformité se constate avec les scénarios ci-dessous ; elle ne se déduit pas de l’intitulé.

### C. Périmètre exact

- **À livrer ou qualifier :** Chargement/validation de la source approuvée par tous les consommateurs avec refus avant effet.
- **Déjà présent :** Settings de production et validateurs HTTP/SMTP/secrets ; base fixée dans settings_base.
- **À conserver :** SQLite permanente, hors Internet, sans Docker/Node/npm sur cible, secrets hors sources/package, données et contrats métier existants.
- **Exclus :** Modification des règles métier, choix d’infrastructure non approuvé, qualification cible ou GO anticipés.
- **Rôles et données :** Exploitant MESS et contributeur autorisés ; composants, configuration et données du profil approuvé.

### D. Acceptation observable

1. GIVEN une configuration valide approuvée WHEN API, workers et scripts démarrent THEN leurs chemins/base/paramètres effectifs SHOULD BE identiques.
2. GIVEN une source approuvée désignant un fichier SQLite hors du code WHEN API et workers de remise/échéance sont lancés THEN tous SHOULD BE ouvrir ce même fichier et utiliser la même URL publique, sans revenir au défaut backend/db.sqlite3.

### E. Vrai refus ou non-conformité

3. GIVEN source divergente, champ obligatoire absent ou secret invalide WHEN un consommateur démarre THEN il SHOULD BE arrêté avant effet avec diagnostic sans valeur sensible.

Le refus doit être observé, avec absence d’effet non autorisé ; une erreur inattendue ne vaut pas un refus conforme.
Les refus additionnels de la source restent applicables. En l’absence d’arbitrage, ces scénarios conditionnels
sont des propositions à finaliser, pas une règle métier adoptée ni une fiche prête par simple présence de Gherkin.

### F. Preuves attendues

Unitaires parsing/précédence ; processus d’intégration API/workers/scripts ; contrats configuration ; E2E technique démarrage, aucun nouveau parcours métier.

Comparer attendu/observé par scénario et variante : SHA/entrées, rôle/jeu, état initial, action, résultat,
preuve et verdict. Les mesures UX reprennent [UX-01 à UX-09](../../../../../docs/quality/ux-acceptance.md) ;
aucun seuil esthétique, RPO/RTO, disponibilité ou capacité MESS supplémentaire n’est inventé.
Un test automatisé ne remplace pas la relecture visuelle ; un rapport local ne vaut pas un PV cible.
